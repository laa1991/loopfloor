# 最简实现公式（三件）

> 四格回答的是**会怎么坏**；这一节回答的是**最少要有什么**。
>
> **一句话：长程任务 = 一个写在盘上的「下一步」 + 一个每轮重新出现的「现在在哪」 + 一个敢丢历史的「压缩」。**

## 1. 公式

| # | 件 | 它负责什么（一句话） | 替哪一格兜底 | 去掉它会怎样 |
|---|---|---|---|---|
| ① | **接续指针** | 把「**下一步**」写在盘上——单数、覆盖式、带来源 | 丢状态 | 换窗口 / 换代之后：要么从零重来，要么照着一份**已经过期**的计划继续 |
| ② | **工作台** | 把**任务态**搬到**每轮都会重新出现**的那个面 | 丢状态 + 偏目标 | 状态还在日志里，**但不在视野里** ⇒ 「下一步做什么」由最近看到的几句话决定 |
| ③ | **压缩** | 让历史**有上限**——把丢得起的丢掉，并**记账** | 上下文爆 | 走不过第一次爆窗；「长程」只剩「一次超长会话」 |

**缺任何一件都不是「少一点」**：

- 只有 ① ⇒ 有接续，但方向会被历史带偏；
- 只有 ② ⇒ 眼前很全，但换一个窗口就断了；
- 没有 ③ ⇒ 到不了需要接续的那一刻，前面两件都用不上。

## 2. 每件后面的理由

### ① 接续指针：因为「下一步」是唯一那件必须活过换代的东西

它不是日志，也不是摘要：**单数、覆盖式、带来源**。历史可以有很多，下一步只能有一个。

理由来自失败样本，不是来自设计品味：**换窗口后的第一轮输入里没有「上次到哪了」**，于是只剩两条路——从零重来（把做过的事重做一遍），或照着一份**看起来还在、但世界已经变了**的计划继续做。两条都不报错。

> ⚠️ **一条反直觉的实测**：当入口被写成两个**并列**选项（「认领一个目标，**或者**继续推进你的下一步」）时，被真正走的是**成本更低的那一条**——两条路的用量差一个数量级（值见 `README.zh.md` §4）。**并列的第二个选项，会变成事实上的默认。**

### ② 工作台：因为「写下来」不等于「在眼前」

压缩之后，目标、计划、已定的事**都还在日志里，但不在视野里**。于是「下一步做什么」不再由**任务态**决定，而由**最近看到的那几句话**决定——不报错，会话照常继续，只是方向慢慢偏掉。

所以 ② 的判据不是「有没有把它写下来」，而是**它有没有在每一轮的开头重新出现**。写下来的东西会被埋掉；**只有会自己重新出现的载体**才在长程尺度上算数。

⚠️ 一条容易搞错的地方：**卡片上的字是渲染面，机制在载体里**。把显示当成机制，会得出「工作台兼职了目标管理」这种错结论——它显示目标，不等于它承担目标。

### ③ 压缩：因为长程任务的第一道墙是窗口上限

压缩不是优化项，是**前提**。但它的代价必须写明：**它是这套东西里唯一会主动删东西的机制**——丢细节、丢上下文里的原话，而且**丢的时候不报错**。

⇒ 正因为它会丢，才需要 ①②：**把丢不起的东西，搬到它碰不到的地方去。**

这也解释了这三件为什么是一套而不是三套：**③ 负责「丢得起」，①② 负责「丢完之后还剩什么」。** 这个关系是本节最要紧的一句——它也是我们当初把这三件放在一起的全部理由。

## 3. 三件怎么咬合

**先说结论**：② 与 ③ 的耦合是**单向的**——**② 读 ③ 的产物，③ 完全不知道 ② 的存在。**

### 3.1 ② 这一侧有四处耦合，指向同一件事：「压缩发生过几次」

| 耦合点 | 它长什么样 |
|---|---|
| 卡片上**直接有一行压缩计数** | `Compacted: N time(s)`——N 来自读「摘要」这条投影，而投影由压缩事件折出来 |
| **「重注入」本身就是耦合** | 「上次发卡之后有没有新摘要落地」这个判断，决定了要不要**重发**一张卡 |
| 卡片上的文件窗口是**压缩那一刻**的冻结快照 | 它标着 `Files (before last compaction):`——即「压缩边界上的落点」 |
| 它**不订阅**任何压缩事件 | 只走投影，不走订阅。压缩落地后的动作是**重发一张新卡**，不是给旧卡贴「已过期」标签（我们特意核过：那张卡上唯一的 `Stale` 标的是**指针**记在目标收尾之前，与压缩无关） |

### 3.2 ③ 那一侧：零引用

③ 的实现里没有一处提到 ②。**压缩只做一件事**：把消息流里的一段换成一条摘要。它是这套里**唯一会改动上下文的动作**，而它改的**不是** system——是一条 `user/message`。

### 3.3 时序：两条路，方向相反

| 压缩由谁触发 | 谁先谁后 |
|---|---|
| **自动压力压缩**（在每回合的准备阶段里） | **压缩先、卡片后**——卡片渲染时，新摘要已经算进去了 |
| **模型自己调压缩工具** / 溢出恢复 / 空闲压缩 | **卡片先、压缩后**——续跑是同一回合的下一步，卡片靠「有新摘要落地」那道口子**补发** |

⇒ 「卡片每回合重钉」这句要加一个限定：**它不是无条件重发的。** 文本与上一张逐字相同、又没有新摘要落地时，它**不发**——这道门的存在，正是为了不让「每回合重钉」变成**每回合打断请求前缀**（前缀一断，整段历史重算）。

### 3.4 一句话

**③ 管「上下文有多长」，② 管「上下文里说的是什么」。**

而 ③ 恰恰是**让卡片消失**的那个动作——卡片本身就是被压缩掉的那段里的消息；同时 ② 又是压缩之后**唯一会自动回来**的那一层。
⇒ 这就是它们为什么是一套：**③ 每删一次，② 就得多钉一次。**

> **证据来源与边界（必须一起读）**
> - 以上机制与行号来自一次**只读代码走查**（工作台包 + 压缩包 + 上游文档），**我没有逐条复核**；引用时按「只来自走查」对待，不当作已二次核过。
> - 「③ 侧零引用」是**两把尺**（ripgrep + `Select-String`）在 **26 个文件**上的读数；覆盖面是仓内，**不含**被 gitignore 的目录与 `node_modules`。
> - **四条触发路径在真实会话里的占比，我们没有量。**
> - `none. The earlier card no longer applies.` 这一行**在真实会话里出现过几次、由哪一条触发，我们也没量**——它在我们这侧是代码上可达、且有单测覆盖其中一半（「关了就不发空卡」），但没有真实的出现计数。

## 4. 「最小」怎么验收（每件一个问句）

| 件 | 判据（一句可测的问句） |
|---|---|
| ① | 换一次窗口 / 压缩一次，**只看第一轮的输入**：有没有「上次到哪了」、有没有「在等什么」？ |
| ② | 把历史全清掉、只留这一轮：你还能说出「在做什么、做到哪、下一步」吗？ |
| ③ | 这条会话里历史占多少？**压的时候丢了什么，有没有记账**？ |

⚠️ 这三条判据**有两侧才算数**：不光要问「该有的有没有」，还要问「**什么输入会让它失败**」——一条判不失败的判据只是装饰（同族讨论见 `docs/05-尺自己也会安静地错.md`）。

## 5. 这份公式不承诺什么

- **不承诺做得对。** 三件齐了照样可以把事做错——那是「偏目标」的下一层，本式不管。
- **不承诺完备。** 三件是**最小**，不是**够用**：第四格「假完成」没有对应的一件，它要的是**装置与账本**，不是又一个载体。
- **不承诺跨平台等价。** 这里只给**形状与判据**；每家的实现可以完全不同——这正是我们只写形状的原因。
- **③ 的记账我们也没全做到。** 「压的时候丢了什么、有没有记账」目前是一条**问句**，不是一条已兑现的承诺；写成问句而不是写成「已实现」，是故意的。
